How it works

From an empty repo to a test your team would write

Ask an agent for a Playwright test and you get a reasonable test for some other project. Cue closes that gap in four steps, and the last one doesn't need an agent at all.

1

Install once

Cue detects your agents, shows a plan, and writes nothing until you say yes. Running it twice changes nothing.

npx @wiluszdamian/cue-cli init
2

Map your app

Survey a live route and Cue records what is really on the page: the button is called "Log in", not #btn-submit-2.

cue survey http://localhost:3000/login
3

Ask for a test

Your agent reads the rules and the map on its own, and looks selectors up instead of guessing them.

cue locator "Log in" --route /login
4

CI holds the line

The same conventions run as ESLint rules. A test that breaks one fails the build, in CI and in the editor, with or without an agent.

eslint . && cue verify --ci
Rules your agent cannot ignore

A document is a suggestion. A failing build is not.

An agent can talk itself past a style guide. It cannot talk itself past a red build. Cue ships your conventions as real ESLint rules, and every message says what is wrong, why, and what to write instead.

  • Messages written for a model. "Violates rule" teaches an agent to route around it; naming the replacement teaches it to fix the test.
  • One source of truth. The rules live in one file. Change it and the ESLint rules, the docs and the agent instructions all update together.
  • Ask any rule why. cue explain no-hard-waits prints the reason and the alternative.

test('pays with a saved card', async ({ checkout }) => {

A map of your actual application

Selectors that exist, with a date attached

Cue writes down what is on each page after actually looking, and reads your product source to cross-check it. Every fact can answer the question "why does Cue believe this?".

  • Confidence you can read. Confirmed in source and seen running, runtime-only, or code-only: the agent knows which locators may move.
  • Freshness, not folklore. Knowledge ages. Stale routes are re-surveyed one at a time instead of re-crawling the whole app.
  • Unknown means unknown. When there is no entry, Cue says so and tells the agent which command fills the gap. It never guesses.

Built for agents

Every install ships an MCP server

Three read-only lookups, small enough to answer a question without eating the context your agent needs for the real task. It runs next to Playwright MCP, not instead of it.

  • explain_rule — why a rule exists, and what to write instead.
  • resolve_owner — which source of advice wins on a topic.
  • resolve_locator — a real selector, with confidence and freshness.
Write a test that a locked-out user sees an error on login.
resolve_locator("Log in", route: "/login") → getByRole('button', { name: 'Log in' }) · confirmed · fresh
resolve_owner("test data strategy") → cue (wins)
explain_rule("require-test-tags") → every test carries a canonical tag from rules/tags.yaml

A tie-breaker for your agent

Cue doesn't teach Playwright. It decides who does.

Your agent loads Microsoft's official Playwright skills, Playwright MCP and a community reference skill. None of them knows the others exist, so when they disagree it picks one more or less at random. Cue installs all three and adds one table that says which source wins.

Topic Decided by
Page objects, locator strategy, test structure and tagging cue (wins)
Your app's selectors, routes and domain vocabulary agent-kb (wins)
Running, debugging, tracing and reports playwright-official
Single scripted browser actions from an agent playwright-mcp
Accessibility, visual regression, Electron and other specialist corners reference-skill
Your repo stays yours

Three promises about your files

♻️

Idempotent

Running init twice changes nothing. Every write goes through a plan you can read first.

🔒

Never overwrites your edits

A file you edited by hand is reported and left alone. Existing files are only touched inside a marked region.

↩️

Exact uninstall

Removing Cue reverses exactly what was installed, from a recorded manifest, not from guesswork.

What we don't claim

Does it make agents write better tests? Not proven yet.

Cue includes a benchmark harness that records and scores agent runs. No benchmark has been run, so we don't claim better tests. What we can show is the mechanism: rules that fail the build, and selectors checked against the running app.

When the numbers exist, they'll be here, including if they're unflattering.

FAQ

Questions, answered

What is Cue?

A sidecar for existing Playwright repositories. It gives AI coding agents your team's testing rules as ESLint rules, and a knowledge base of your application's real routes and selectors in .agent-kb/. It doesn't replace Playwright or your framework.

Do I need an AI agent to use it?

No. The ESLint rules work on their own, in CI and in your editor, and catch the same mistakes from people. The agent wiring is a bonus, not a requirement.

Which agents does it support?

Claude Code, Cursor, Codex, Grok, Gemini CLI and OpenCode. Every agent reads AGENTS.md, so the baseline applies even to one Cue doesn't detect.

Why the scoped package name?

Always install @wiluszdamian/cue-cli. Running an unscoped name with npx on a machine that hasn't installed it can fetch an unrelated package. Once it is installed locally, the short command is enough.

Does it work on an existing, messy test suite?

That's the main target. Cue is built for brownfield repositories: it leaves files it doesn't own alone, and the knowledge base is useful long before the app is fully mapped.

Does it need a hosted service?

No. Everything runs locally: the CLI, the ESLint plugin, the knowledge base and the MCP server. Node.js 22.13 or newer is the only requirement.
