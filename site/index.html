The running order

Four cues from an untouched repo to a test your team would sign off. The last one runs in CI with no agent in the room.

Cue Called when Command What happens
1 Once per repo npx @wiluszdamian/cue-cli init Detects your agents, prints a plan and writes nothing until you say yes.
2 Per route, when it changes cue survey <url> Records what is really on the page into .agent-kb/, with a date.
3 Whenever you want a test Ask your agent It reads the rules and the map on its own and looks selectors up instead of guessing.
4 Every push eslint . && cue verify --ci A broken rule fails the build. Map drift fails the check.
The book is law. A document is a suggestion; a red build is not.

Rules your agent can't talk past

Your conventions ship as real ESLint rules. Every message says what is wrong, why, and what to write instead, because "violates rule" teaches an agent to route around it and naming the replacement teaches it to fix the test. 

tests/checkout.spec.ts
  14:3  error  no-hard-waits

  waitForTimeout waits on the clock, not on the app. Wait on the
  state you actually care about with a web-first assertion, which
  retries until the condition holds: await expect(locator).toBeVisible(),
  .toHaveText(), .toBeEnabled(). For a network round-trip, use
  await page.waitForResponse(...).

Blocking notes: where everything actually stands on stage.

A map of the app, with a date on every entry

Cue writes down what is on each page after actually looking, and cross-checks it against your source. Every entry can answer one question: why does Cue believe this? 

$ cue locator "Log in" --route /login

Route:      /login
Locator:    getByRole('button', { name: 'Log in' })
Test id:    login-submit
Confidence: confirmed
            Present in the product source
            and seen running.
Freshness:  fresh

Confidence says whether a locator was confirmed in source and at runtime, seen only at runtime, or found only in code. The agent knows which ones may move.

Unknown means unknown. With no entry, Cue says so and names the command that fills the gap. It never hands back a plausible guess.

Verify reports exactly what it checked against the running app:

Cue doesn't teach Playwright. It decides who does.

Your agent may load Microsoft's Playwright skills, Playwright MCP and a community reference skill. None of them knows the others exist. Cue installs them and adds one table that says which source wins on each topic.

Topic Decided by
Page objects, locator strategy, test structure, tagging cue wins
Your app's selectors, routes and vocabulary agent-kb wins
Running, debugging, tracing, reports playwright-official
Single scripted browser actions playwright-mcp
Accessibility, visual regression, Electron reference-skill
Three lookups over MCP, read-only
  • explain_rule Why a rule exists and what to write instead.explain_rule("no-hard-waits")
  • resolve_owner Which source wins on a topic.resolve_owner("test data strategy") → cue
  • resolve_locator A real selector, with confidence and freshness.resolve_locator("Log in", "/login")
House rules. Posted by the stage door.

Your repo stays yours

  • Running init twice changes nothing

    Every write goes through a plan you can read first.

  • Your edits are never overwritten

    A file you changed by hand is reported and left alone. Existing files are touched only inside a marked region.

  • Uninstall is exact

    Removal reverses what was installed from a recorded manifest, not from guesswork.

Previews, not opening night.

Does it make agents write better tests? Not measured yet.

Cue includes a harness that records and scores agent runs. No benchmark has been run, so we don't claim better tests. What you can check today is the mechanism: rules that fail the build, and selectors verified against the running app. The numbers will go here when they exist, whatever they say.

Questions from the house.

Questions

Do I need an AI agent to use it?

No. The ESLint rules work on their own, in CI and in your editor, and catch the same mistakes from people.

Which agents does it set up?

Claude Code, Cursor, Codex, Grok, Gemini CLI and OpenCode. Every agent reads AGENTS.md, so the baseline applies even to one Cue doesn't detect.

Does it work on an existing, messy suite?

That's the main target. Cue leaves files it doesn't own alone, and the map is useful long before the whole app is surveyed.

Why the long package name?

Always install the scoped @wiluszdamian/cue-cli. An unscoped name run through npx can fetch an unrelated package. Once installed, the short cue command is enough.

Does anything leave my machine?

No. The CLI, the ESLint plugin, the map and the MCP server all run locally. There is no hosted service.

Getting started

Introduction

Cue helps you and your AI agent write Playwright tests that match how your team already works.

If you have asked an agent for a test and got back something that looked right but used a button that doesn't exist, or ignored every convention in your project, Cue is built for that problem.

The two things it does

Checks your testsRules that run on every save and every push. A test that breaks one fails the build, not the code review. Learns your appIt visits your app, writes down what is on each page and remembers, so nobody guesses what a button is called.

Why guessing is the expensive part

An agent has never seen your app. Ask it for the log-in button and it invents something plausible, like #login-btn. The test then fails as if your app were broken, and somebody spends an afternoon debugging a login page that works.

Note

When something isn't in the map, Cue says "I don't know, go and look" instead of guessing. That refusal is the point.

What it isn't

  • Not a Playwright tutorial. Playwright's own docs are kept current by the people who build it. Cue points you at them.
  • Not a replacement for your process. It has opinions about tests, none about your roadmap or tickets.
  • Not magic. It stops an agent from inventing details it doesn't have. It can't explain a feature nobody has explained.
Getting started

Quickstart

Add Cue to a Playwright project in about five minutes.

Before you start

You need Node.js 22.13 or newer. Cue works with npm, pnpm, yarn and bun and detects which one you use.

Set it up

  1. Run init

    From the folder your tests live in, or will live in. It finds your agents, lists every file it wants to create and why, and waits. Nothing is written until you say yes. 

    npx @wiluszdamian/cue-cli init
    pnpm dlx @wiluszdamian/cue-cli init
    yarn dlx @wiluszdamian/cue-cli init
    bunx @wiluszdamian/cue-cli init

  2. Finish the install

    init prints the remaining steps for your package manager, usually the dev dependencies and the browsers. 

    npx playwright install

  3. Check the wiring

    Every problem doctor reports comes with the exact command that fixes it. 

    npx @wiluszdamian/cue-cli doctor

  4. Survey a page, then ask for a test

    Map the pages your tests touch, then ask your agent. It reads the rules and the map on its own. 

    cue survey http://localhost:3000/login

What you get

File What it's for
AGENTS.md The house rules, in the file every agent reads on its own
eslint.config.mjs Turns the rules into checks that run
tests/, pages/, fixtures/ Where things go, with a working example of each
.agent-kb/ Where knowledge about your app is stored
Tip

Already have a suite and only want the rules? Run init --bare to skip the folder layout.

Look things up

cue locator "log in button"

When there is no entry, Cue refuses and names the command that fills the gap. A tool that guesses here is worse than no tool.

Confidence

Value Meaning
confirmed In your app's code and seen on the page.
runtime-only Seen on the page, not found in your code. It may come from a library and may move.
code-only In your code, never seen. It may be dead or behind a feature flag.
Note

Commit .agent-kb/. Values that look like passwords, tokens or email addresses are stripped before writing, but read the first commit anyway.

Your application

Keep the map current

Apps change. verify checks the map against the running app and says plainly what it did not check.

Run it

cue verify --base-url http://localhost:3000

Verdicts

Verdict Means
PASS Every route was checked and matches.
PARTIAL Some routes were checked; the rest were not.
NOT VERIFIED Nothing was looked at, for example no --base-url.
FAIL Drift, an unreachable route or an unreadable file.
EMPTY Nothing has been surveyed yet.

In CI

--ci exits 1 on FAIL only. --ci=strict exits 1 unless the verdict is PASS, so "nobody looked" is never a green build. 

cue verify --base-url $STAGING_URL --ci=strict

Re-survey one route

When a single route is stale, survey that route again instead of crawling the whole app.

Reference

Commands

Every command, with what it is for.

init

Sets up a project. Shows the plan first and waits for a yes. Without a terminal it applies nothing unless you pass --yes.

--target <a,b>string

Set up for specific agents.

--bareflag

Skip the Playwright folder layout.

--yesflag

Do not ask. Required without a terminal.

--forceflag

Overwrite files you edited. Use with care.

doctor

Checks everything is wired up. --ci fails on errors; --offline skips network checks.

survey <url>

Visits a page and records what is on it. --from <file> reads a snapshot captured elsewhere.

locator <element>

Looks up a selector with its confidence and freshness. --route narrows it to one page.

verify

Checks the map against the app. See Keep the map current.

explain <rule-id>

Why a rule exists, and what to write instead.

uninstall

Removes exactly what init installed, from the recorded manifest.
